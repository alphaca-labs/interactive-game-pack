# Rush Counter 제작 계획

> **구현 경로는 `games/game-06/` 다.** 이 문서가 아니라 `games/game-06/game.json` 이 경로·슬러그·견적의 근거이며, 목록·링크는 `games/*/game.json` 을 글롭해 만든다(검증: `scripts/check-hub.mjs`). 아래 본문의 경로는 실제 디렉터리에 맞춰 갱신했다.

## 1. 한 줄 약속과 범위

**45초 동안 세 조리대를 동시에 돌리고, 몰려드는 주문을 정확히 서빙한 뒤 현금 더미를 걷어 160코인을 버는 한 손 레스토랑 러시.** 주문을 먼저 읽고 조리를 병렬로 예약하는 판단, 완성 음식이 상하기 전 수거하는 긴장, 서빙 후 정산까지 챙기는 리듬을 짧은 세션에 압축한다.

- 근거: `outputs/frames/group2-112s.png`, `outputs/frames/group2-140s.png`, `outputs/frames/group2-160s.png`의 두 번째 패널에서 확인되는 손님 대기열, `버거 ×1` 주문 말풍선, 조리 설비, 현금 HUD `69 → 200 → 500`, 카운터의 지폐 더미를 메커닉 근거로 삼는다. 원본 로고·캐릭터·화면 구성은 복제하지 않는다.
- 제작 가정: 영상에서 확인되지 않은 조리 시간, 주문 분포, 성공·실패 조건과 연출은 아래 수치로 고정한다.
- 산출물: 외부 라이브러리·폰트·이미지·공유 코드 없이 단독 실행되는 `games/game-06/index.html`, `style.css`, `script.js` 3개 파일.
- 범위: 한국어 UI, 단일 45초 레벨, 시작 안내, 플레이, 성공/실패, 다시 하기, 음향 설정까지. 광고 SDK, 분석 SDK, 서버, 결제, 다국어, 추가 레벨은 제외한다.

## 2. 30–60초 플레이 루프

1. 시작 화면에서 목표 `45초 / 160코인 / 손님 3명 놓치면 종료`와 조작을 보고 `시작`을 누른다.
2. 첫 주문과 세 조리대를 확인한 뒤 첫 조리대 입력을 하면 시프트가 시작되고 45초 타이머가 감소한다.
3. 맨 앞 손님의 말풍선에서 버거·감자·음료 조합과 인내 게이지를 읽는다.
4. 필요한 조리대를 탭해 동시에 조리하고, 완료된 조리대를 다시 탭해 보관대에 수거한다.
5. 보관 수량이 주문을 만족하면 활성화되는 `서빙`을 누른다. 음식이 차감되고 기본 금액·속도·연속 보너스가 합산된 현금 더미가 계산대에 생긴다.
6. 계산대의 현금 더미를 탭해 HUD 보유 코인으로 정산한다. 여러 건을 모아 한 번에 걷을 수 있지만, 수거 전 금액은 목표에 포함되지 않는다.
7. 다음 손님이 전진하는 동안 다음 주문을 예상해 미리 조리한다. 완성품 방치로 폐기되거나 손님을 놓치면 연속 보너스가 끊긴다.
8. 수거한 코인이 160에 도달하면 즉시 성공, 손님 3명 이탈 또는 제한 시간 종료 시 목표 미달이면 실패한다. 결과 화면에서 보유 코인, 미수거 금액, 서빙 수, 놓친 손님, 폐기 수, 최고 연속을 보여 주고 다시 시작할 수 있다.

모든 런의 첫 손님은 항상 `버거+음료`다. 최초 런에서는 해당 조리대가 순서대로 맥동하고, 첫 조리 입력 전에는 시간과 인내가 흐르지 않는다. 다시 하기에서도 첫 조리 입력 전 정지는 유지하되 맥동 안내는 반복하지 않는다.

## 3. 규칙과 밸런스

### 조리·보관

| 조리대 | 단축키 | 조리 시간 | 완료 후 유예 | 단가 | 상태 표현 |
|---|---:|---:|---:|---:|---|
| 버거 그릴 | `1` | 3.2초 | 3.0초 | 20코인 | 굽기 진행 원, 연기 |
| 감자 튀김기 | `2` | 2.5초 | 3.5초 | 15코인 | 기포 진행, 황금색 점등 |
| 음료 머신 | `3` | 1.2초 | 5.0초 | 10코인 | 컵 수위, 넘침 경고 |

- 빈 조리대를 누르면 조리를 시작한다. 조리 중 재입력은 무시하되 짧은 `조리 중` 상태 문구를 표시한다.
- 완료된 조리대를 누르면 해당 음식 1개를 보관한다. 음식별 보관 한도는 2개다. 한도에서 수거를 시도하면 `보관대가 가득 찼어요`를 표시하고 완료 유예는 계속 흐른다.
- 유예가 끝나면 `폐기` 상태가 된다. 폐기 상태 조리대를 한 번 눌러 청소하면 빈 상태로 돌아가며 보유 코인 3 차감(최저 0), 연속 서빙 초기화, 폐기 수 +1이 적용된다.
- 보관 음식은 상하지 않는다. 주문은 같은 음식을 중복 요구하지 않으므로 2개 한도는 다음 주문 선조리용이다.
- 세 조리대는 서로 독립적으로 진행되며 동시에 조리할 수 있다.

### 주문·대기열

- 런 초기화 때 활성 손님 1명과 `QUEUED` 손님 2명을 만든다. 활성 손님이 정산되면 300ms 퇴장하고, 첫 대기 손님이 300ms 진입한 뒤 `ACTIVE`가 된다. 이때 열린 꼬리 자리는 0.8초 후 새 `QUEUED` 손님으로 채워 총 3명을 유지한다. 퇴장·진입 중에는 활성 손님이 없고 모든 인내가 정지하지만 시프트와 조리는 계속 흐른다.
- 활성 손님만 인내가 감소한다. 기본 인내는 12초이며, 30초 경과 후 생성된 손님은 10초다. 뒤 손님의 인내는 감소하지 않는다.
- 주문은 고객이 생성되는 순간 시드 난수로 확정·저장하며 중복 없는 음식 집합이다. 직전 주문과 완전히 같으면 최대 3회 재추첨하되, 3종 전체 주문처럼 대안이 없으면 반복을 허용한다. 말풍선은 활성 손님 것만 공개하고 대기 손님 주문은 숨겨, 선조리는 정확한 예고가 아니라 분포를 읽는 선택으로 남긴다.

| 시프트 경과 | 주문 크기 가중치 | 의도 |
|---|---|---|
| 0–12초 | 1개 60%, 2개 40% | 조작 학습 |
| 12–30초 | 1개 25%, 2개 60%, 3개 15% | 병렬 조리 유도 |
| 30–45초 | 1개 10%, 2개 55%, 3개 35% | 마감 러시 |

- 인내가 0이 되면 손님이 이탈하고 놓침 +1, 연속 서빙 0이 된다. 퇴장 300ms와 다음 손님 진입 300ms 후 새 손님의 인내가 시작된다.
- 놓침이 3이 되는 즉시 실패한다. 손님 퇴장·진입 중에도 시프트 시간과 조리는 계속 흐른다.

### 서빙·현금 수거·점수

- 보관대가 활성 주문의 모든 항목을 포함하면 `서빙` 버튼이 활성화된다. 누르면 필요한 음식만 1개씩 차감하며 여분 재고는 남는다.
- 미완성 주문에서는 실제 `disabled` 버튼과 인접한 `음식 N개 더 필요` 문구를 표시하고 `aria-describedby`로 연결한다. 게임 표면에서 서빙 단축키를 눌렀을 때만 손실 없이 같은 안내를 `aria-live`로 알린다.
- 기본 지급액은 사용한 음식 단가 합이다.
- 속도 보너스는 서빙 시 남은 인내 비율에 따라 `max(1, ceil(남은 비율 × 5))`코인, 범위 1–5다.
- 서빙 직전에 `새 연속 횟수 = 현재 연속 + 1`로 올리고, 연속 보너스는 `min(max(새 연속 횟수-1, 0) × 3, 9)`코인이다. 놓침·폐기 시 현재 연속은 0이 된다.
- 서빙 시 `지급액 = 기본 + 속도 + 연속`을 계산해 `pendingCash`에 더하고 현금 더미 수를 1 늘린다. 이때 `bankedCash`와 HUD 목표 진행도는 아직 변하지 않는다. 현금 더미는 최대 3단으로만 그리되 금액과 건수는 제한 없이 누적한다.
- 현금 더미를 누르면 `bankedCash += pendingCash`, `pendingCash = 0`, 더미 수 `0`을 한 번에 적용한다. 빈 계산대 입력은 무시한다. 현금은 상하거나 사라지지 않지만, 시간 종료 시 남아 있는 미수거 금액은 목표와 결과 보유 코인에 포함하지 않아 수거 행동의 의미를 유지한다.
- 이벤트별 원장을 쓴다. `SERVE`는 미수거 금액만 생성하고, `COLLECT_CASH`만 보유 코인을 증가시킨다. `WASTED` 청소는 그때 한 번만 `bankedCash = max(0, bankedCash - 3)`을 적용하며 미수거 금액은 건드리지 않는다. 각 이벤트를 서로 다시 계산하지 않는다.
- 목표는 **수거한 160코인**이다. 현금 수거로 160에 도달하는 순간 성공 판정 후 게임 시간을 멈춘다. 성공 등급은 목표 달성으로 1별, 남은 시간 8초 이상이면 2별, 남은 시간 15초 이상이면서 놓침 0이면 3별이다.
- 시간 0에서 `bankedCash < 160`이면 실패한다. 같은 프레임에 현금 수거와 시간 종료가 겹치면 입력 이벤트의 수거 정산 후 종료를 판정한다. 서빙만 하고 수거하지 않은 현금으로는 성공하지 않는다.
- 매 프레임 처리 순서는 `접수된 입력 정산 → 조리대 시간 전이 → 고객 인내 전이 → 시프트 시간 전이 → 종료 판정`이다. 종료 우선순위는 `입력 정산 후 bankedCash 160 이상(성공) → 놓침 3(실패) → 시간 0·목표 미달(실패)`로 고정한다. 따라서 같은 프레임의 세 번째 이탈과 시간 종료는 이탈 실패로 기록되고, 유효한 현금 수거로 먼저 목표를 넘기면 성공한다.

### 기준 난이도와 튜닝 허용폭

- 목표 플레이어는 6–8명 서빙, 0–1명 놓침, 0–2개 폐기로 성공한다.
- 내부 시드 6 기준 숙련 QA 성공률 70–85%, 첫 플레이 성공률 35–55%를 목표로 한다.
- 성공률이 낮으면 순서대로 목표를 150으로 낮추고, 인내를 +1초, 완료 유예를 +0.5초 조정한다. 높으면 역순으로 되돌리되 조리 시간을 늘리지 않는다.
- 화면 문구와 판정 상수는 `CONFIG` 한 곳에 두며, 프레임률과 무관하게 `performance.now()` 기반 경과 시간으로 계산한다.

## 4. 명시적 상태 머신

### 전체 게임

`BOOT → INTRO → READY → PLAYING → RESOLVING → WON | LOST`, 결과의 `다시 하기 → READY`

- `BOOT`: DOM·설정·최고 기록 초기화. 로드 완료 후 `INTRO`.
- `INTRO`: 규칙과 시작 버튼 표시. 시간·인내 정지. 시작 입력으로 모든 런 데이터를 초기화하고 `READY`.
- `READY`: 첫 주문과 조리대를 표시하되 시간·인내는 정지한다. 첫 유효 조리대 입력을 해당 조리대에 적용한 뒤 `PLAYING`.
- `PLAYING`: 입력, 조리, 인내, 대기열, 미수거 현금, 보유 코인을 갱신. 목표 달성·3회 이탈·시간 종료 중 하나만 최초로 수락하고 `RESOLVING`.
- `RESOLVING`: 0.7초 동안 마지막 현금 수거 또는 실패 연출. 추가 게임 입력 차단. 판정 원인에 따라 `WON`/`LOST`.
- `WON`/`LOST`: 결과 모달, 기록, 다시 하기. `다시 하기`로 `INTRO`가 아닌 새 `READY`에 진입하며 튜토리얼 맥동은 생략한다.
- 브라우저가 숨겨지면 `PAUSED` 플래그를 겹쳐 타이머 기준점을 보정하고, 복귀 시 `계속` 버튼으로 재개한다. `Esc`/`P`도 같은 플래그를 토글하되 `INTRO`, `RESOLVING`, 결과 상태에는 적용하지 않는다.

### 조리대(각각 독립)

`IDLE --입력→ COOKING --조리시간→ READY --수거→ IDLE`

`READY --유예만료→ WASTED --청소입력/3코인차감→ IDLE`

- `COOKING`은 `startedAt`, `readyAt`; `READY`는 `wasteAt`을 가진다.
- `READY` 수거 시 보관 한도면 상태를 유지한다. `WASTED`는 자동 복구하지 않는다.
- 게임 종료·재시작은 모든 조리대를 `IDLE`로 강제 초기화한다.

### 손님·주문

`QUEUED → ENTERING → ACTIVE → SERVED | EXPIRED → EXITING → REMOVED`

- 고객 생성 때 주문과 난수 소비를 확정하고, `ACTIVE` 진입 때 인내 시작 시각만 확정한다.
- 주문은 `OPEN → READY_TO_SERVE → FULFILLED | EXPIRED`. 재고 변동 때마다 주문 집합 포함 여부를 다시 계산한다.
- `FULFILLED`와 `EXPIRED`는 상호 배타적이다. 한 손님에 대한 지급액 생성·놓침 정산은 `settled` 가드로 1회만 실행한다.

### 계산대 현금

`EMPTY --서빙 정산→ PENDING --추가 서빙→ PENDING --수거→ EMPTY`

- `PENDING`은 `pendingCash`, `bundleCount`, 마지막 증가 시각을 가진다. 서빙 한 건당 `bundleCount +1`, 시각 표현은 `min(bundleCount, 3)`단으로 제한한다.
- `COLLECT_CASH`는 현재 `pendingCash` 스냅샷을 한 번만 `bankedCash`로 옮긴다. 120ms 액션 잠금과 트랜잭션 ID로 빠른 이중 입력에도 중복 적립되지 않는다.
- 일시정지 중에는 수거할 수 없고, 게임 종료 시 미수거 현금은 결과에 별도 표시한 뒤 재시작 때 `0`으로 초기화한다.

### 입력

각 action 키는 `AVAILABLE → PRESSED → LOCKED(120ms) → AVAILABLE`; 종료/일시정지는 `DISABLED`다. 잠금은 조리대·서빙·현금 수거별로 따로 적용해 서로 다른 조리대의 빠른 병렬 입력을 막지 않는다. 포인터·터치·키보드는 모두 동일한 `dispatchAction(action)`으로 합쳐 이중 탭과 `pointer`/`click` 중복 정산을 막는다.

## 5. 화면 구성과 조작

### 세로 360 × 640 기준

1. 상단 12%: 보유 코인 `0/160`, 원형 45초 타이머, 놓침 하트 3개, 음소거·일시정지.
2. 고객 구역 28%: 맨 앞 손님과 큰 주문 말풍선, 인내 막대; 뒤 손님 둘은 작게 겹쳐 대기열 깊이를 보인다.
3. 카운터/보관대 16%: 음식별 아이콘과 `0/2`, 중앙 `서빙` 버튼, 금액·건수가 표시된 64px 이상의 현금 수거 버튼. 미수거 현금이 있으면 `현금 42 · 2건 수거`처럼 행동과 결과를 함께 적는다.
4. 주방 34%: 버거·감자·음료 3개 조리대를 한 행으로 배치. 각 카드 전체가 64px 이상 탭 영역이며 진행률·상태 텍스트·단축키를 함께 표시한다.
5. 하단 10%: 상황 문구와 첫 판 안내. 기기 안전 영역을 패딩에 포함한다.

### 입력 체계

- 포인터/터치: 조리대 탭으로 시작·음식 수거·폐기, `서빙` 탭으로 주문 제출, 현금 더미 탭으로 보유 코인에 정산한다. 드래그와 길게 누르기는 사용하지 않는다.
- 키보드: `1/2/3` 조리대, `4` 또는 `C` 현금 수거, 게임 표면 또는 서빙 버튼에 포커스가 있을 때 `Space` 서빙, `P` 또는 `Esc` 일시정지, `R` 결과 화면 다시 하기. `Enter`는 전역으로 가로채지 않고 포커스된 버튼의 기본 동작만 수행한다. `Space`도 다른 조리대·현금·음소거·일시정지 버튼에 포커스가 있으면 그 버튼의 기본 동작을 유지한다. `Tab` 순서는 HUD 설정 → 조리대 1–3 → 서빙 → 현금 수거 순이다.
- 모든 인터랙션은 최소 44×44px, 명확한 `:focus-visible` 3px 외곽선, 버튼의 실제 `disabled` 속성을 사용한다.

## 6. 비주얼·모션·오디오

### 절차적·오리지널 자산

- 음식, 조리대, 동전, 하트, 손님은 직접 작성한 단순 기하형 인라인 SVG 또는 CSS 도형으로 만든다. 외부 이미지, 원작 로고·캐릭터·스크린샷, 시스템 이모지는 사용하지 않는다.
- 손님은 피부·상의·앞치마 색, 머리 형태, 안경 유무를 시드로 조합해 8개 이상 실루엣을 만든다. 사람을 희화화하지 않는 중립적 형태를 쓴다.
- 따뜻한 크림색 카운터, 토마토 레드 강조, 민트색 준비 완료, 호박색 경고, 자주색 실패를 사용하되 상태는 색만이 아니라 아이콘·텍스트로 중복 표시한다.
- 폰트는 시스템 산세리프 스택만 사용한다. 모든 SVG에 장식용 `aria-hidden="true"`, 의미 정보는 인접 텍스트로 제공한다.

### 모션

- 손님 진입/퇴장 300ms, 주문 말풍선 팝 180ms, 조리 진행은 CSS 원형 게이지로 표현한다. 서빙 시 180ms로 지폐 더미가 쌓이고, 현금 수거 시 지폐 1장이 계산대에서 HUD로 450ms 이동한다. HUD 증가는 수거 입력과 동시에 확정하고 이동은 후행 연출로만 쓴다.
- 준비 완료 조리대는 800ms 간격의 2px 호흡, 폐기 직전 마지막 1초는 테두리 점멸, 성공은 600ms 별 확산, 실패는 250ms 가벼운 좌우 흔들림 1회만 사용한다.
- `prefers-reduced-motion: reduce`에서는 이동·확산·흔들림·호흡을 제거하고 80ms 이하의 색/불투명도 전환과 즉시 위치 변경으로 대체한다. 진행률과 타이머는 숫자·막대로 계속 전달한다.

### 오디오

- 사용자 첫 입력 뒤 Web Audio API로 짧은 합성음만 생성한다: 조리 시작 저음 클릭, 완료 2음 상승, 서빙 벨, 현금 수거 3음 상승, 폐기 저음, 마지막 5초 틱, 성공/실패 코드.
- 기본 음량 35%, HUD 음소거 토글 제공, `localStorage`에는 음소거와 최고 보유 코인만 저장한다. 오디오 미지원·차단 시에도 게임과 피드백은 완전하게 동작한다.

## 7. 접근성·반응형

- `lang="ko"`, 의미 있는 `button`, HUD와 주문의 텍스트 레이블, 결과 모달 포커스 트랩·닫힘 방지, 일시정지 시 포커스 복귀를 적용한다.
- `aria-live="polite"` 영역에는 `감자 준비 완료`, `손님 이탈`, `현금 32코인 생성`, `32코인 수거, 총 96코인` 같은 중요한 사건만 순차 전달한다. 초 단위 타이머와 조리 진행은 매 프레임 읽지 않는다. 마지막 5초만 5, 3, 1초를 알린다.
- 일반 텍스트/배경 4.5:1, 큰 숫자·아이콘 3:1 이상 대비를 유지한다. 색각에 관계없이 상태명, 패턴, 아이콘을 함께 쓴다.
- 320–480px 세로에서는 `clamp()`로 크기를 조절하고 세로 스크롤 없이 안전 영역 안에 맞춘다. 높이 600px 미만이면 대기 손님 그림과 장식 여백을 줄이되 활성 주문·인내·조리대는 축소하지 않는다.
- 폭 700px 이상 또는 가로 화면에서는 최대 960px의 2열 레이아웃으로 전환해 왼쪽에 고객/HUD, 오른쪽에 보관대/주방을 둔다. 게임 콘텐츠 최대 폭을 제한해 조리대 간 이동 거리가 과도하게 늘지 않게 한다.
- 200% 브라우저 확대에서는 결과·시작 화면이 내부 스크롤 가능하며 핵심 버튼이 가려지지 않는다. `touch-action: manipulation`, `overscroll-behavior: none`으로 의도치 않은 확대·페이지 바운스를 줄인다.

## 8. 독립 파일 구현 개요

### `games/game-06/index.html`

- 시작 패널, 게임 HUD, 고객/주문, 보관대, 세 조리대, 현금 수거 버튼, 상태 알림, 일시정지·결과 모달의 의미 구조를 선언한다.
- 외부 URL이나 공유 헤더/푸터를 참조하지 않고 `style.css`, `script.js`만 상대 경로로 로드한다.
- 캔버스 없이 DOM과 인라인 SVG 템플릿을 사용해 확대·접근성·디버깅을 단순화한다.

### `games/game-06/style.css`

- 색·간격·타이밍을 CSS 변수로 관리하고 세로 기본 레이아웃, 2열 미디어 쿼리, 안전 영역, 터치 크기, 포커스, 고대비 상태, 모달을 정의한다.
- 진행률은 `--progress`, 인내는 `--patience`, 조리 상태는 `data-state`로 표현한다.
- `prefers-reduced-motion`과 `prefers-contrast: more` 대체 스타일을 포함한다.

### `games/game-06/script.js`

- 단일 IIFE와 `CONFIG`, `state`를 두고 `Station`, `Customer`, `CashTray` 데이터 객체 및 순수 함수 `createOrder`, `canServe`, `calculatePayout`, `advanceStation`, `settleCustomer`, `collectCash`를 구성한다.
- `requestAnimationFrame` 루프는 실제 경과 시간으로 시프트·인내·조리를 갱신하고, DOM 쓰기는 값이 바뀐 요소에만 수행한다.
- 모든 입력은 `dispatchAction`; 전이는 `transitionGame`, `transitionStation`, `transitionCustomer`에서 검증한다. 종료 판정은 한 프레임 1회, 정산은 `settled` 가드로 보호한다.
- `visibilitychange`, 키보드, 포인터, 음향, 저장소 오류를 처리한다. `localStorage` 실패는 메모리 값으로 조용히 대체한다.
- `?seed=6`은 주문을 재현하고 `?test=1`은 화면 렌더 전 순수 함수 자기 테스트 결과를 콘솔에 출력한다. 프로덕션 기본 URL에는 디버그 UI를 노출하지 않는다.

## 9. 인수 시나리오

1. **첫 진입:** 새 세션에서 시작 전 2초를 기다려도 타이머와 첫 손님 인내는 줄지 않고, 첫 주문과 조리대 안내가 보인다.
2. **병렬 조리:** 버거·감자·음료를 연속 입력하면 세 진행률이 독립적으로 흐르고 각 설정 시간에 `READY`가 된다.
3. **수거 한도:** 같은 음식 재고가 2일 때 완료품 수거를 시도하면 재고는 2, 조리대는 `READY`이며 유예는 계속 감소한다.
4. **폐기:** 완료품을 유예 끝까지 두면 `WASTED`; 청소 시 보유 코인이 3 감소하되 0 아래로 내려가지 않고 연속이 0이 된다.
5. **정확한 서빙:** 주문이 버거+음료이고 해당 재고가 있으면 서빙 한 번에 각각 1개만 빠지고 기본 30코인과 보너스가 미수거 현금에 한 번만 더해진다. 보유 코인은 아직 변하지 않는다.
6. **현금 수거:** 서빙 두 건의 현금이 쌓인 뒤 계산대를 한 번 누르면 두 건의 합계가 보유 코인에 정확히 한 번 더해지고 미수거 금액·건수가 0이 된다. 빈 계산대와 빠른 이중 탭은 추가 적립하지 않는다.
7. **미완성 방지:** 필요한 재고가 없으면 서빙 버튼이 비활성이고 포인터·키보드 어느 쪽도 현금이나 재고를 바꾸지 않는다.
8. **손님 이탈:** 활성 인내가 0이면 놓침이 정확히 1 증가하고 다음 손님이 활성화된다. 세 번째 놓침은 즉시 실패를 예약하며 중복 정산되지 않는다.
9. **경계 프레임:** 미수거 현금이 있어도 시간 0이면 목표에 포함하지 않는다. 시간 0 프레임에 유효한 현금 수거가 먼저 처리되어 보유 코인 160 이상이면 성공하고, 서빙만 완료했거나 수거 후 미달이면 실패한다.
10. **일시정지:** 탭 전환 또는 `P`로 5초 멈췄다가 복귀해도 시프트·조리·인내가 그 5초만큼 진행되지 않는다.
11. **재시작:** 결과에서 다시 하기를 누르면 보유·미수거 현금, 시간, 재고, 조리대, 대기열, 놓침, 연속이 초기값이고 이벤트 리스너가 중복되지 않는다.
12. **입력 동등성:** 동일 시드에서 터치/마우스와 `1/2/3`, `4/C`, `Space`가 같은 전이와 정산을 만든다. 빠른 이중 입력도 한 번만 처리된다.
13. **접근성·반응형:** 320×568, 390×844, 844×390, 1024×768 및 200% 확대에서 핵심 상태·버튼이 접근 가능하고 가로 스크롤이 없으며, 축소 모션 설정에서 큰 이동/점멸이 사라진다.

## 10. 검증 계획

- 순수 로직 자기 테스트: 주문 중복 금지·단계별 가중치, 재고 집합 판정, 지급액·미수거·보유 코인 원장, 현금 이중 수거 방지, 최저 0/연속 상한, 조리 경계 시각, 고객 1회 정산, 승패 우선순위, 시드 재현성을 `?test=1`에서 assertion으로 검증한다.

- 밸런스 QA: 시드 10개를 초심자 5회·숙련자 10회 플레이해 성공률, 평균 보유·미수거 코인, 서빙/놓침/폐기/현금 수거 횟수, 조리대 유휴율을 기록한다. 목표 범위를 벗어나면 3장의 튜닝 순서만 적용한다.
- 회귀 체크: 각 게임 폴더만 정적 서버 루트로 열어 네트워크 요청 0건, 콘솔 오류 0건, 다른 게임 파일/전역/스토리지 키와 충돌 0건을 확인한다. 저장 키는 `rushCounter.muted`, `rushCounter.best`로 한정한다.

## 11. 견적과 일정 근거

- 유형: **D — simulation / very-high**.
- 기준 견적: **1,200만–1,600만원(VAT 별도)**, **15–20영업일**, 시니어 HTML5 개발자 1명 + UI/아트·QA 부분 투입, 1회 승인/수정 기준.
- 4주 최대 제작량: 동일 구성의 1트랙은 **1개**, 공용 셸과 아트 가이드를 공유하는 2트랙 병렬 운영은 **2개**다. 러시 카운터 1종만 제작하면 1트랙으로 4주 내 완료 가능하다.
- 입력 공수: 로직 6일(세 조리대·고객·주문·경제·승패의 동시 상태 머신과 밸런스), 아트/UI 4일(세 조리대 상태, 음식, 고객 조합, HUD·모달·반응형), QA 3일(시간 경계, 터치/키보드, 모바일 브라우저, 접근성, 난이도). 합계 13일에 기획 정리, 통합, 기기 검수, 1회 수정 2–7일을 더한 범위다.
- 8종 팩의 첫 구현으로 선택되어 부트·입력·HUD·리사이즈 템플릿까지 새로 만들면 프로젝트 공통 공수 **+2영업일**을 한 번만 별도 배정한다. 각 게임은 배포 시 파일을 독립 보유하므로 런타임 결합은 만들지 않는다.
- 상단 금액은 상태/캐릭터 원화 볼륨, 동시 타이머 경계 버그, 실제 기기 밸런스 반복을 반영한다. 합성음 대신 별도 음원 제작, 브랜드 일러스트, 분석·광고 SDK, 다국어, 추가 레벨은 별도 견적이다.
