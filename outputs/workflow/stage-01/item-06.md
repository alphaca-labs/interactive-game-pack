## 근거와 제작 가정

`outputs/frames/group2-112s.png`, `group2-140s.png`, `group2-160s.png`의 두 번째 패널을 다시 확인했다. 프레임에서 직접 확인되는 정보는 손님 대기열, `버거 ×1` 주문 말풍선, 복수 조리 설비, 카운터의 지폐 더미, 현금 HUD `69 → 200 → 500`이다. 따라서 **조리·서빙뿐 아니라 현금 더미를 직접 수거하는 단계**를 독립 입력과 상태로 기획에 포함했다.

영상만으로 확정할 수 없는 조리 시간, 주문 분포, 인내 시간, 목표·실패 조건은 프로토타입 가정으로 분리했다. 단일 45초 레벨에서 수거한 160코인을 목표로 하며, 이 수치는 밸런스 QA 결과에 따라 150까지 한 번 조정할 수 있다. 원본 로고·캐릭터·스크린샷·화면 배치는 사용하지 않는다.

## 기획 핵심 결정

- **동시 상태머신:** 버거·감자·음료 조리대가 각각 `IDLE → COOKING → READY → WASTED`로 독립 진행하고, 고객은 `QUEUED → ACTIVE → SERVED/EXPIRED`로 이동한다. 조리·고객·타이머가 같은 프레임에서 충돌해도 판정 순서를 고정했다.
- **현금은 별도 원장:** 서빙은 지급액을 `pendingCash`에만 쌓고, 현금 더미 수거만 `bankedCash`를 올린다. 수거 전 금액은 목표에 포함되지 않으며, 빠른 이중 탭은 트랜잭션 ID와 120ms 잠금으로 중복 적립을 막는다.
- **명확한 경계 판정:** 프레임 처리 순서는 입력 정산 → 조리대 → 고객 인내 → 시프트 시간 → 종료다. 시간 0 프레임에 유효한 현금 수거가 먼저 처리되어 보유 코인 160 이상이면 성공하고, 서빙만 끝난 미수거 금액으로는 성공하지 않는다.
- **짧은 러시 밸런스:** 초반은 1–2개 음식 주문, 후반은 2–3개 주문 비중을 높인다. 숙련 QA 성공률 70–85%, 첫 플레이 35–55%, 6–8명 서빙을 기준으로 목표 금액 → 인내 → 완료 유예 순서만 조정한다.
- **입력 동등성:** 포인터·터치 탭과 키보드 `1/2/3` 조리대, `4/C` 현금 수거, `Space` 서빙을 동일한 `dispatchAction` 경로로 처리한다. 모든 타깃은 44px 이상이며 키보드만으로 완주할 수 있다.
- **외부 에셋 0:** 음식·설비·지폐·손님을 오리지널 인라인 SVG/CSS 조합으로 제작하고 Web Audio 합성음만 사용한다. 라이브러리·폰트·이미지 다운로드가 없어 에셋 라이선스 추적 항목이 없다.

## 개발 단계 인계

- 구현 위치는 `games/rush-counter/`이며 `index.html`, `style.css`, `script.js` 세 파일만으로 독립 실행한다. 외부 URL·CDN·공유 런타임을 참조하지 않는다.
- 우선순위는 (1) 가짜 시계 기반 상태 전이와 이벤트 원장, (2) 세 조리대·주문·현금 입력, (3) DOM/인라인 SVG 표현, (4) 접근성·반응형·오디오, (5) 실기기 밸런스 순이다.
- `?seed=6`으로 주문을 재현하고 `?test=1`에서 주문 분포, 지급액/현금 원장, 이중 수거, 0초 경계, 고객 1회 정산을 assertion으로 검증한다.
- 인수 시나리오 13개를 기획서에 명시했다. 핵심 게이트는 병렬 조리, 재고 한도, 폐기 차감, 미완성 주문 방지, 현금 합산 수거, 0초 우선순위, 일시정지, 재시작, 입력 동등성, 4개 뷰포트와 200% 확대다.
