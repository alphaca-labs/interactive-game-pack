# 플레이트 스택 (Plate Stack) — 작업 항목 3 / 8

6줄로 쌓인 접시 중 **맨 위 한 장만** 집어 카운터의 손님 2명이 요구하는 요리를 채우는 60초 보드 퍼즐이다.
집은 접시는 보관대(3칸)를 거쳐 주문에 자동 충전되고, 해소 뒤에도 보관대 3칸이 막히면 실패한다.

- 기획서: `outputs/plans/plate-stack.md`
- 유형: `B — 보드상태 퍼즐` · 출처 `00:06` (6초 그룹)
- 실행: `games/game-03/index.html` 을 그대로 열면 된다. 빌드·서버·네트워크가 필요 없다.

## 규칙 요약

| 항목 | 값 |
|---|---|
| 보드 | 6컬럼 × 4장 = 접시 24장, 컬럼당 최상단 1장만 탭 가능 |
| 주문 | 8건(동일 요리 3장), 카운터 활성 2건 + 대기열 미리보기 |
| 보관대 | 3칸. 해소 패스 후에도 3칸이 차면 실패 |
| 시간 | 60초. 초과 시 실패 |
| 점수 | 주문 기본가(40/80/120/200/300) × 콤보(1.0→1.2→1.5) + 클리어 시 남은 시간 × 5 |

## 해결 가능성 보장

무작위 셔플은 보관대 3칸으로 못 푸는 배치를 만든다. 그래서 **역방향 생성**을 쓴다.

1. 실제 규칙 엔진으로 정방향 시뮬레이션하며 정답 픽 시퀀스 `P` 를 만든다(보관은 트레이 점유 2 이하에서만 삽입).
2. `P` 를 역순으로 컬럼에 쌓는다. 역순 push = 정방향 pop 이므로 각 컬럼에서 인덱스가 작은 접시가 항상 위에 온다 → `P` 는 반드시 유효한 수순이다.
3. 생성 직후 `P` 를 규칙 엔진에 그대로 돌려 클리어되는지 자체 검증한다. 실패하면 최대 20회 재생성 후 검증된 고정 시드로 폴백한다.

규칙은 DOM 을 모르는 순수 함수(`pick` / `resolve` / `isLost` / `isCleared`)라 **생성 검증기와 게임 본체가 같은 코드**를 쓴다.

## 검증

| URL 파라미터 | 용도 |
|---|---|
| `?test=500` | 시드 500개 생성 → 정답 수순 재생 → 클리어 자동 검증. 화면·콘솔에 결과 출력 |
| `?seed=42` | 고정 보드로 재현 (QA·버그 리포트용) |

`window.PlateStack` 에 규칙 엔진과 `debug()` 스냅샷을 노출한다. 게임 로직은 이 표면을 호출하지 않는다.

측정된 난이도(엔진 시뮬레이션): 앞을 안 읽으면 40%, 2수 앞 60%, 3수 앞 78% 클리어. 실패가 배치 운이 아니라 선택에서 갈리도록 잡았다.

## 기획서와 다르게 구현한 2가지

1. **아래 접시도 아이콘으로 보인다.** 기획서는 "두께 선으로만" 이었지만, 그러면 무엇을 먼저 집을지 고를 근거가 없어져 실패가 운으로 읽힌다(엔진 시뮬레이션에서 정보 없는 플레이의 클리어율이 45% 에서 더 오르지 않았다). 집을 수 있는 건 여전히 최상단 1장뿐이고, 아래 장들은 작고 흐리게 눌러 위계를 유지했다.
2. **대기 손님을 인원수 대신 다음 주문 3건으로 보여 준다.** "지금 필요 없는 접시를 왜 보관하는가" 가 선택이 되려면 다음 주문이 보여야 한다.

두 변경 모두 기획서의 플레이어 약속("실패는 운이 아니라 내 선택 때문이라고 느껴져야 한다")을 지키기 위한 것이다.
